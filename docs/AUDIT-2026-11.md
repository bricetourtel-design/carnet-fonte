# Audit du projet Gymon — 11 novembre 2026

Objet : état des lieux complet du dépôt à la version `2026-11-11 i` (cache `carnet-fonte-v49`), en vue de préserver les fonctionnalités et la logique de développement du MVP, et de préparer une migration vers un autre compte.

Méthode : lecture intégrale de `index.html`, `sw.js`, `manifest.json`, des six suites de tests, de la documentation et de l'historique git ; exécution des six suites de tests dans un environnement Chromium. Pas de test sur iPhone réel dans cette session.

Résultat en une phrase : **le MVP est complet, cohérent, documenté et testé ; les risques sont ailleurs que dans le code, dans la pérennité des données utilisateurs, la propriété du nom et la dépendance à une seule personne.**

## 3. Ce qui fonctionne bien

- **Cohérence doc / code / tests.** Chaque règle de `ALGORITHME.md` et `CREATURE.md` se retrouve dans le code avec le même vocabulaire, et dans un test. Rare pour un MVP.
- **Paramétrage centralisé** : `CREATURE_CFG`, `FATIGUE`, `RANGES`, `REST_BY_RANGE`, `REC_BASE`, `STD`, `WEIGHT`, `SYN`. Les réglages sont lisibles sans lire les algorithmes.
- **Migrations de données soignées** : `creatureState()` gère les Gymon d'avant (seuils, couleur, vitalité, 4 → 13 formes), `creatureFixLevels()` rejoue la musculature, `loadLocal()` migre le profil, `OFF_OLD` convertit les anciennes raisons. Personne ne perd rien à une mise à jour.
- **Sécurité des entrées** : `esc()` partout dans les templates, `cleanImport()` avec `safeId` sur tout ce qui finit dans un attribut HTML, CSV parsé proprement, fichiers d'import jamais exécutés.
- **Confidentialité** : aucune requête réseau sauf les deux compteurs GoatCounter (désactivables, inactifs en test et en local) et la mise à jour du service worker. Les données de santé et de cycle sont explicitement exclues du partage d'image.
- **Hors ligne** : stratégie claire (page toujours fraîche en ligne, cache sinon ; photos depuis le cache), rechargement automatique une fois à la nouvelle version.
- **Explicabilité** : chaque proposition du coach a un « pourquoi ? », chaque ajustement de séance est listé, chaque raison de séance a une conséquence écrite.

## 4. Risques et faiblesses

### 4.1 Données des utilisateurs (risque élevé)
- Stockage `localStorage` uniquement : limité à quelques Mo, effaçable par Safari après 7 jours sans visite hors écran d'accueil (atténué par le rappel d'installation et `navigator.storage.persist()`), perdu si l'utilisateur change de téléphone sans export.
- Export = texte JSON à copier-coller. Peu de testeurs le feront.
- **Le stockage est lié à l'origine (domaine)**. Changer l'URL de l'app à la migration revient à effacer le Gymon et l'historique de tous les testeurs, sauf export/import manuel. C'est le point à traiter en premier (voir `docs/MIGRATION.md`).
- `c.fed` est plafonné à 1 000 identifiants : au-delà, une très vieille séance pourrait théoriquement être recomptée à une résurrection. Cas marginal, à noter.

### 4.2 Propriété et droits

Contenu déplacé dans le document Claude privé du propriétaire (sujets business et propriété hors du dépôt public, décision du 11 novembre 2026).

### 4.3 Technique (risque moyen, accepté pour un MVP)
- Un seul fichier de 3 234 lignes, lignes longues, pas de typage, pas de linter. Lisible pour l'auteur et pour une IA qui lit le bloc entier ; difficile pour un nouveau développeur. Un découpage serait un projet en soi et n'est pas recommandé avant la validation du MVP.
- Deux numéros de version à incrémenter à la main (`APP_VERSION`, `CACHE`). Oublier le second laisse les téléphones sur l'ancienne version. Un test pourrait vérifier que `CACHE` change quand `index.html` change.
- `sw.js` précharge 170 photos (3,9 Mo) à l'installation : première installation plus lente sur mauvais réseau, mais l'app est ensuite complète hors ligne. Choix défendable.
- Code mort mineur : `muscleLevels()` (remplacée par la croissance v2), `inferFeel()` qui retourne toujours 3, `setStatus`, `saveWorkout`, `removeWorkout` sans effet. Sans danger ; à retirer un jour avec un test de référence mis à jour.
- Aucune intégration continue : les tests ne tournent que si on les lance. Un workflow GitHub Actions (Node + Playwright, Chromium) les lancerait à chaque push.
- Tests sur Chromium uniquement. Les comportements spécifiques iOS (son, wake lock, partage, `navigator.standalone`) ne sont vérifiés qu'à la main.
- La branche `claude/accueil-premier-lancement` sur le dépôt distant date du 29 octobre avec un historique réécrit : à supprimer pour éviter une confusion.

### 4.4 Produit (points d'attention, pas des défauts)
- Mélange tutoiement (tutos, bulles) et vouvoiement (coach, réglages). Cohérent par zone, à trancher avant une communication publique.
- Français uniquement, textes dans le code. Une internationalisation demanderait une extraction préalable.
- Référence de force « femmes » par simples coefficients (×0,6 et ×0,75) : indicatif, assumé dans l'app.
- Aucune mesure de l'effet de la créature sur la régularité (hypothèse de départ non encore testée chiffrée). Les deux compteurs GoatCounter mesurent l'adoption, pas la rétention.

### 4.5 Organisation
- Tout le contexte était dans la tête du propriétaire et dans des conversations. Ce dépôt documenté (`CLAUDE.md`, `docs/`) est la réponse ; il faut le tenir à jour.
- Retours testeurs : un fichier interne, bien tenu, anonyme. À continuer.

## 6. Recommandations, par ordre

1. **Avant la migration** : fixer l'URL de production définitive, ou prévoir le parcours d'export/import pour les testeurs. Détail dans `docs/MIGRATION.md`.
2. **Avant toute valorisation** : voir la liste du document privé.
3. **Intégration continue** : un workflow qui lance les six suites à chaque push. Faible effort, grand gain.
4. **Sauvegarde plus simple** : export en fichier (téléchargement) plutôt que texte à copier, toujours sans serveur. Réduit le risque de perte de données.
5. ~~**Supprimer la branche obsolète** sur le dépôt distant.~~ Fait le 11 novembre 2026 : elle contenait encore des captures avec des données personnelles retirées de `main`. Il ne reste que `main` (et la branche de travail de Claude).
6. **Garder la discipline actuelle** : doc à jour dans le même commit, test de référence figé avant toute modification volontaire, `WHATS_NEW` réservé aux vraies nouveautés.
7. **Ne pas refondre** l'architecture avant la validation du MVP par les testeurs. Le fichier unique est un choix, pas une dette, tant que le produit n'a pas trouvé son marché.
